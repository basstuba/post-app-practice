# 設計書の作成案 → 相談 → 作成 → 注記

対象：$ARGUMENTS

設計書の型は CLAUDE.md の「設計書の型」が決めている（7 節の見出しと順、先頭は `# <機能名>機能 設計書` と `Issue: <URL>`）。この Skill はその型に沿った**進め方**を持つ。型そのものはここに写さず、毎回 CLAUDE.md を読む。

## A. 作成案の提示 → 相談 → 作成

### 1. 読む

- `gh issue view <N>`（背景・完成の条件・仕様・守ること）。Issue 番号が不明なら `gh issue list --state all` から機能名で探して確認する。
- CLAUDE.md の「設計書の型」と「変えないもの」。
- 直近の設計書（`docs/tag.md`・`docs/bookmark.md`・`docs/search.md` など）。**注記が付いていても、それは完成後の記録なので、新しい設計書には写さない。** 書き方（表の粒度、ER 図、メッセージ一覧）を揃える材料にする。
- 関係する既存コード（ルート、コントローラー、モデル、ビュー、`lang/ja/validation.php`、`tests/Feature`）。名前や仕様が既存と被らないか確かめる。

### 2. 作成案を提示する（まだファイルを作らない）

1. 冒頭に「Written for: …」の 1 行（この設計書で実装・レビューする人と Claude）と、「まだ作成していません」の一言。
2. 7 節それぞれの要点（決めたこと、テーブルの列、画面と遷移、ルート、入力チェックとメッセージ、テスト観点の柱）。
3. **相談したい点**：番号を付けて 2〜5 個。それぞれに**推奨案と理由**を添える（依頼者が「1.も2.も提案のままで」と番号で答えられるように）。Issue で決まったことは蒸し返さない。
4. Issue の「完成の条件」を、設計書の「受け入れ条件」に**勝手に増やさない**。足したい内容は相談点として出す。

### 3. 相談で直す

指示を反映して**全文を出し直す**。連動する節も直す。末尾に「前回からの変更点」と、残る確認点（無ければ「この内容でよければ作成します」）。

### 4. 作成する

「作成してください」と言われたら、承認された最新の案で `docs/<機能名>.md` を作る。

- **先頭に注記を入れない。** 注記は機能の実装が完了してから（B）。
- 日本語。該当しない節も見出しは残し、「〜は無い」と書く。コードはまだ書かない。
- 作ったら、どこに何を作ったかだけ報告する。**コミット・push は、依頼されたときだけ**行う。ブランチを切る／切らない、main に push する、は依頼の指示に従う（設計書だけのときは「ブランチは作らなくてよい」と言われることが多い）。コミットメッセージは `<機能名>機能の設計書を追加` の形（機能追加ではないので `tutorial13-N:` は付けない）。

## B. 実装時点の記録の注記を追記する

**実装・テスト・レビューが終わり、PR がマージされたあと**にだけ行う。それより前に頼まれても、まだなら「マージ後に追記します」と伝えて止める（実装と同時に足さない）。

1. `docs/<機能名>.md` の先頭（タイトルの前）に、次の 1 行と空行を足す。文言は一字も変えない。すでに付いていれば何もしない。
   `> この設計書は、この機能を実装した時点の記録です。このあとは更新していません。`
2. 本文は直さない。実装で食い違った点があっても、ここでは触らず報告だけする。
3. コミットメッセージは `<機能名>機能の設計書に実装時点の記録である旨の注記を追加`。push は依頼されたときだけ。

## やらないこと

- 承認前のファイル作成、コードの実装
- Issue で決まったことの蒸し返し、受け入れ条件の無断追加
- `answers/` の参照、`docs/13-N/`（学習者の設計書）の変更
- 注記を作成と同時に入れること

# イシュー作成案の提示 → 相談 → 作成

機能追加の要件から、イシューを **案として提示し、相談で固めてから作成する**。依頼者が「作成案を提示してください」と言っている間は、`gh issue create` を実行しない。作るのは、依頼者が「作成してください」と明示したあとだけ。

## 入力

依頼文に次が書かれていることが多い。足りない部分は「決まっていない部分」として、案の中で提案する。

- 背景（いまの困りごと・やりたいこと）
- 決まっていること（選び方・データの用意のしかた・名前・権限など）
- 受け入れ条件（依頼者が書いたもの）
- 決まっていないこと（「あなたと相談して決める」と言われた部分）

## 手順

### 1. 現状のコードと過去の Issue を読む

案を現実に合わせるため、提示の前に読む。コードは直さない。

- 関係するもの：`routes/web.php`、対象のコントローラー・モデル・ポリシー、`database/migrations`・`seeders`・`factories`、対象のビュー、`lang/ja/validation.php`、`tests/Feature`、`docs/`
- 既存の似た概念（例：トピックとタグ、いいねと新機能）との違いを確かめ、名前や仕様が被らないようにする
- `gh issue list --state all` で過去の Issue を見て、直近の機能追加の Issue を `gh issue view <N>` で読み、**本文の型**を揃える
- CLAUDE.md の「変えないもの」と「設計書の型」を確認する。機能のために「変えないもの」へ触れる必要があるなら（例：タイムラインに絞り込みを足す）、イシューに明記して、触れる範囲を限定する

### 2. 作成案を提示する

次の順で、日本語で書く。1 回目から完成形に近い案を出す。

1. 冒頭に「Written for: …」の 1 行（このイシューを実装・レビューする人と Claude、など）と、「まだ作成していません」の一言
2. **タイトル案**（ラベルは過去の機能追加に揃える。通常は `enhancement`）
3. **イシュー本文案**（下の「本文の型」）
4. **実装の見通し**：テーブル・モデル・コントローラーなど、イシューには書かない補足。落とし穴があればここで知らせる（例：リダイレクトで絞り込みが外れる）
5. **相談して決めたい点**：2〜5 個に絞る。それぞれ **推奨案と理由**を添える

決めるときの注意：

- 依頼者が決めたことは、そのまま入れる。蒸し返さない
- 決まっていない部分は、候補と理由を示して推奨を 1 つ言う（名前を決めるなら、既存の似た概念と区別できる理由を添える）
- 依頼者が書いた**受け入れ条件は勝手に増やさない**。足したい内容は「仕様」の表に入れ、増やした場合はそう伝える
- 依頼文を解釈した箇所は「〜と読みました」と明示して、確認できるようにする

### 3. 相談で直す

依頼者の指示を反映して、**全文を出し直す**（差分だけで済ませない）。末尾に次を添える。

- 「前回からの変更点」を箇条書きで
- まだ残る確認点があれば、絞って（無ければ「この内容でよければ作成します」）

依頼者の指示が仕様の別の箇所に影響するときは、連動する箇所も直す（例：「既存データを触らない」→「守ること」と「動作確認」にも書く）。

### 4. 作成する

依頼者が「作成してください」と言ったら、承認された最新の全文で作る。

1. 本文をスクラッチパッドの Markdown ファイルに書く（案の「イシュー本文案」の中身そのまま。「実装の見通し」などは入れない）
2. `gh issue create --title "…" --label enhancement --body-file <ファイル>`
3. 返ってきた URL を報告する。次の段階（設計書 `docs/<機能名>.md` の作成など）を一言添える

## 本文の型

過去の機能追加の Issue（いいね #8 など）に揃える。見出しは `##`。

1. **背景**：いまの困りごとと、やりたいこと
2. **完成の条件**：チェックボックスで、依頼者の受け入れ条件をそのまま。1 行 1 条件
3. **仕様（決定事項）**：「項目｜内容」の表。次を漏らさない
   - 入口・押せる人／付け替えてよい人（認可）、未ログインの扱い
   - 選べるもの・名前・用意のしかた（シーダーなど）、既存データをどう扱うか
   - 画面の表示（付いていないときの見え方、該当 0 件の文言を含む）
   - 存在しない ID・不正な値の扱い（404 など）
   - 削除したときの連動（`cascadeOnDelete`）
   - 入力チェックとメッセージ（日本語、`lang/ja/validation.php`）
   - 保存・実行後の遷移
4. **守ること（変えないもの）**：CLAUDE.md の「変えないもの」から今回関係するものと、依頼で指定されたもの。足すだけの変更なら「〜を足すだけ。ほかは現状維持」と書く
5. **動作確認の進め方**（必要なときだけ）：データの入れ方や手順に特別な事情があるとき（例：既存データを触らないので、動作確認で画面から付ける）
6. **設計書**：`docs/<機能名>.md` を CLAUDE.md の「設計書の型」で作る、と書く。作らない場合は理由を書く（いいね #8 は学習目的のため作らなかった）。PR 本文の判定は、このイシューの「完成の条件」に対して行う

## やらないこと

- 承認前の `gh issue create`
- コードの変更、設計書の作成（それは作成後の別の作業）
- 依頼者が決めたことの蒸し返し、受け入れ条件の無断追加
- `answers/` の参照や、`docs/` の学習者の設計書の上書き

# PR 差分レビュー

PR の差分を読み、設計書どおりか・守るはずの場所が壊れていないか・中身に問題がないかを報告する。**読むだけで、コードは直さない。** 直すかどうかは人が報告を見て決めるため、この Skill の仕事は「人が判断するための材料を、根拠つきで並べる」ことにある。

## 入力

- PR 番号（`#2` など）。無ければ `gh pr list --state merged` で候補を出して確認する。
- 突き合わせる設計書。通常は `docs/<機能名>.md`（PR の変更ファイルに含まれていることが多い）。無ければ Issue 本文か PR 本文を代わりにし、「設計書が無かったので Issue と照合した」と報告に書く。

## 手順

### 0. 差分を取る

`gh pr diff <N>` をスクラッチパッドのファイルに保存して読む（1000 行を超えることがあり、端末に直接流すと読み落とす）。`gh pr diff <N> --name-only` で変更ファイルの一覧も先に取る。

### 1. 設計書と突き合わせる

設計書を全部読み、差分と照らす。見るのは **「書いていないものが増えていないか」**。

- 設計書の「追加・変更されるクラス」「ルート」「増えるテーブル」に無いファイル・クラス・ルート・列がある
- 設計書の「付随して行うこと」「変えないもの」の範囲を超えた変更がある（CLAUDE.md や既存テストの書き換え、文言の追加など）
- 依存の追加：`composer.json` / `composer.lock` / `package.json` が差分に含まれるか。**含まれない場合も「変更なし」と明記する**（無いことの確認が報告の価値になる）
- 設計書の受け入れ条件・テスト観点に対応するテストがあるか（実行はしない。存在だけ見る）

設計書が実装に先立って「決めない」と書いた箇所（例：Factory を足すかは実装時に決める）は、増えていても逸脱ではなく OK とする。

### 2. 触っていないはずの場所を見る

対象は、設計書の「変えないもの」と CLAUDE.md の「変えないもの」から決める。引数で指定があればそれを優先する。典型例は `routes/web.php`、既存のコントローラー・ポリシー、タイムライン（`posts.index`）のビュー。

各ファイルについて、次の順で見る。

1. **消えた行（`-` の行）から先に**見る。足された行より、消えた・置き換わった行のほうが「既存の動きが変わった」ことを示すため。
2. 消えた行が無ければ「消えた行は 0 行」と書く。差分に出てこないファイルは「変更されていません」と書く。
3. 置き換わっている場合は、判定（通る・通らない）・文言・並び順・リンク先・見え方（CSS を含む）のどれが変わるかを分けて書く。リファクタで見た目の挙動が同じでも、**入力の癖（配列・空・改行）での挙動が変わっていないか**を考える。
4. 旧コードの挙動を「こうなるはず」と推測で書いたときは、実行して確かめていないと明記する。

### 3. 中身を読む

次の観点を、差分の新規・変更コードに対して見る。

| 観点 | 見ること |
|---|---|
| N+1 | 一覧・詳細で関連を先読み（`with` / `load`）しているか。ビューのループ内で `@can` やリレーションがクエリを出していないか |
| 認可の置き場所 | 更新・削除でコントローラーが `authorize` しているか。ポリシーの比較が既存の `PostPolicy` と同じ書き方か。設計書が「ログイン済みなら誰でも」としている操作に余計な認可が無いか |
| マスアサインメント | `$fillable` に `user_id` などが入っていても、`create()` に渡す値がサーバー側の値と検証済みの値だけか（リクエスト全体を渡していないか） |
| XSS | `{!! !!}`、`@php` 内の出力、`style` 属性への埋め込みに、ユーザー入力が入っていないか |
| CSRF | `POST/PUT/DELETE` のフォームに `@csrf`（と `@method`）があるか。ミドルウェア設定まで読んでいなければ「読んでいない」と書く |
| 入力チェック | ルール・上限・日本語メッセージ・エラー時の入力保持。`lang/ja/validation.php` に **使っていないルールの訳が混ざっていないか**、型違い（配列など）で訳キーがそのまま出る穴が無いか |
| 書き方の揃い | 既存コードのコメント密度・命名・idiom、テストなら `.claude/rules/testing.md`（`#[Test]`、日本語メソッド名、見出しコメント、Factory の `for()`、失敗ケースで DB 不変の確認） |

### 4. 行番号を確かめる

報告の行番号は **PR の時点のファイルの行**で書く。差分のハンクヘッダ（`@@ -a,b +c,d @@`）から数えるか、`grep -n` で引く。`grep -n` で引くのは作業ツリーのファイルなので、その後の PR で変わっていないことを `git diff <PR のマージコミット> HEAD --stat -- <ファイル>` で確かめてから使う。変わっていたらハンクから数える。

## 判定の付け方

| 判定 | 意味 |
|---|---|
| OK | 読んだ範囲で問題なし。根拠（どの行が何をしているか）を一言添える |
| 要確認 | 設計書・「変えないもの」・既存の決まりと食い違う、または意図が差分から読み取れない。**人が決める** |
| 対象外 | この PR の範囲では判定の必要がない（例：既存の形式を踏襲しただけの箇所） |
| 判定できない | 情報が足りない。**何が足りないか**を必ず書く（テスト未実行、設定ファイル未読、Issue 未読、実行して挙動を確かめていない、など） |

「問題なさそう」で済ませず、見ていないことは見ていないと書く。OK を並べるだけの報告は、読んでいない部分を隠してしまう。

## 報告の形式

1 つの表にまとめる。列は **観点｜判定｜ファイル:行｜気づいたこと** の順で、1 観点 1 行。`1.` `2.` `3.` の節ごとに表を分けてよい。ファイル名は `[PostController.php:41-47](app/Http/Controllers/PostController.php#L41-L47)` のようにリンクにする。

表のあとに、次の 2 つを書く。

1. **判定できなかったこと**：実行していないテスト、読んでいない Issue・PR 本文、確かめていない設定や挙動を、箇条書きで。
2. **人が自分の目で読むべき場所を 3 つまで**：差分を全部読む時間が無い人が、ここだけ見ればよいという場所。選ぶ基準は「要確認が出た箇所」「既存の動きに触れている箇所」「認可・書き込みなどの事故が大きい経路」。それぞれ、なぜ読むべきかを一言添える。

最後に「コードは直していません」と一言添える。

## やらないこと

- コードの修正、コミット、PR へのコメント投稿。依頼されていない。
- テストの実行。依頼があったときだけ行う（回すと結果の件数・成否を報告に含める）。
- `answers/` や `docs/` を答え合わせの目的で書き換えること。

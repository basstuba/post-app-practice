# worktree への修正指示文を作る

メインの作業ツリーで見つかった指摘（レビュー・UAT・テスト失敗）を、worktree の実装担当 Claude に貼れる 1 つの指示文にまとめる。**指示文を出すだけで、コードは直さない。** 直し方は worktree 側が考える。

## 入力

- 指摘の出どころは、この会話に出ている結果（`/code-review`、`/pr-diff-review`、`/uat-browser-check`、`receive-worktree` のテスト結果）。足りなければ、どれを材料にするか確認する。レビューや UAT をこの Skill の中でやり直さない。
- 機能名（`$ARGUMENTS`。無ければ会話から読み取る）と、対応する設計書 `docs/<機能名>.md`。

## 手順

1. **材料を集める**：会話中の指摘を、出どころごとに全部拾う。
2. **重複をまとめる**：複数の出どころが同じ箇所を指していたら 1 件にし、出どころを併記する。
3. **直すもの／判断が要るものに分ける**
   - 直すもの：設計書・受け入れ条件・「変えないもの」と食い違う、またはバグ・テストの不備。
   - 判断が要るもの：好み、設計書に無い提案、直すと「変えないもの」に触れそうなもの。指示文には入れず、人に確認する。
4. **各件を「該当箇所＋内容」で書く**：`ファイル:行`、いま何が起きているか（再現手順や実測があれば添える）、どうなっているべきか（設計書の該当節）。**修正方法・コード案は書かない。**
5. **指示文を出す**：全体を 1 つのコードブロックにして（そのままコピーできるように）、直すものと判断が要るものを分けて提示する。

## 指示文の型

```
Written for: worktree で修正する Claude（実装担当）。修正方法は含めず、該当箇所と内容だけを書いています。

対象：<機能名>（docs/<機能名>.md、Issue #N）

## 直してほしい点
1. <ファイル:行>｜<出どころ>
   内容：<いま起きていること>。<あるべき姿（設計書の節）>
2. …

## 守ること
- テストは書く・直すだけで、実行しない（worktree では hook が止める。実行はメインで行う）
- 設計書の「実装時点の記録」の注記は、PR のマージ後に別途追記するので、触らない
- CLAUDE.md の「変えないもの」（タイムラインの今の動きなど）は変えない
- 直したらコミットして push する（ブランチは worktree-<機能名> のまま）
```

依頼で個別の指定があれば、「守ること」にそのまま足す・差し替える。

## やらないこと

- コードの修正、コミット、push
- 修正方法・コード案を指示文に含めること（依頼者が「該当箇所と内容だけ」としている）
- 受け入れ条件や設計書の変更を、指示文の中でこっそり求めること（変えたいときは「判断が要るもの」として人に聞く）
